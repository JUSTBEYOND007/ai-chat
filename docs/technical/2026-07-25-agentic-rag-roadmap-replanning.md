# Agentic RAG 路线重规划

日期：2026-07-25

## 背景

项目已经具备 Tool Calling、结构化 SSE、Agent Trace、Token Budget 和 Summary Memory。新的改进建议包括 Query Rewrite、混合检索、阈值与多样性、真实取消、检索缓存、异步文档入库和检索调试面板。

这些能力都适合 Flow-Chat，但如果作为七个独立功能平行开发，会产生三个问题：

- 无评测基线，无法说明 Query Rewrite、重排或缓存是否真正有效；
- 后端检索策略与前端 Trace 分离，最后仍像隐藏实现而非完整产品能力；
- 同时引入模型改写、缓存、队列和重排，故障边界过多，面试时难以自圆其说。

因此本次将路线重新组织为三个纵向阶段：检索质量闭环、真实取消、异步入库。

## 建议采纳结论

| 能力 | 是否加入 | 新优先级 | 调整后的定位 |
| --- | --- | --- | --- |
| Query Rewrite | 是 | P0 | 只对依赖历史或口语化问题执行，失败回退原问题 |
| pgvector + 全文混合检索 | 是 | P0 | 语义召回和精确关键词召回双路并行 |
| 阈值与结果多样性 | 是 | P0 | 阈值由评测校准；去重相邻 chunk，并限制单文档数量 |
| 融合/重排 | 是 | P0/P1 | 先用可解释 RRF；模型 reranker 必须用指标证明收益 |
| 检索调试面板 | 是 | P0 | 与后端检索元数据同迭代完成，升级现有 Agent Trace |
| 真正停止生成 | 是 | P0 | 独立阶段，解决取消状态、资源回收和前端竞态 |
| 检索缓存 | 是 | P2 | 正确性和评测完成后再优化；必须包含权限与索引版本 |
| BullMQ 异步入库 | 是 | P1 | 检索闭环后开发，突出任务状态机、幂等和失败补偿 |

## 为什么先做评测基线

混合检索不是“SQL 多查一路”就算完成。至少要回答：

- 精确错误码是否比纯向量更容易命中？
- Query Rewrite 是否提升模糊追问召回，还是改变了用户意图？
- 阈值降低了多少无关引用，是否同时损伤可回答问题？
- 多样性策略是否减少重复 chunk，又是否漏掉连续上下文？
- 模型 reranker 的质量收益是否值得额外延迟和成本？

因此第一步是保存当前纯向量 baseline，并建立 Hit@K、MRR、拒答率和延迟指标。之后每项策略都有对照组，项目亮点才能从“用了很多技术”变成“通过数据验证了技术取舍”。

## 检索闭环目标架构

```text
用户问题 + 最近历史 + Summary Memory
  -> 是否需要 Query Rewrite
  -> originalQuery / rewrittenQuery
  -> pgvector 语义候选
  -> PostgreSQL tsvector 关键词候选
  -> RRF 排名融合
  -> 最低可信阈值
  -> 相邻 chunk 去重 / 单文档数量限制 / 可选 MMR
  -> RAG Token Budget
  -> knowledge_search 结构化结果
  -> Agent 最终回答与严格一致的引用
  -> Agent Trace / 检索调试面板
  -> 离线评测报告
```

## 关键技术取舍

### Query Rewrite 不是每次都调用

完整、独立的问题直接检索。只有存在代词、上下文省略或明显口语化表达时才改写，避免增加每轮模型延迟和费用。改写异常、超时或空结果必须回退原问题。

### RRF 与 reranker 区分

RRF 是将两个排名列表融合的确定性算法，具有稳定、可解释和无需额外模型的优点，但它不是语义 reranker。第一版先完成 RRF、阈值和多样性；只有评测证明仍有明显排序问题时，再增加 cross-encoder 或 LLM reranker。

### 文档新鲜度不是默认相关性

企业知识库中的旧规范可能仍然有效，盲目给新文档加权会降低准确性。只有文档具有版本、有效期或公告时效等明确元数据时，才将新鲜度作为可配置特征，并在 Trace 中解释其影响。

### 缓存必须绑定权限和索引版本

检索缓存 key 不能只有 query。至少包含：

```text
userId + knowledgeBaseId + knowledgeBaseVersion + normalizedQueryHash
```

Embedding 缓存还必须包含模型名或模型版本。文档新增、删除或重新向量化后，旧检索缓存必须失效，避免返回已删除内容。

### 真实取消独立成阶段

当前前端关闭 SSE 只能停止显示，不能回收服务端模型和工具资源。真实取消涉及 generation 所有权、AbortController 生命周期、持久化状态、SSE 竞态和幂等接口，适合独立迭代，不能作为一个按钮顺手补上。

### 异步入库晚于检索质量

BullMQ 很有全栈亮点，但它解决吞吐和可靠性，不解决检索准确性。先证明“入库后的内容能被正确检索”，再优化“大文档如何可靠入库”，开发叙事更完整。

## 新的迭代顺序

### 迭代 6：评测基线与检索协议

- 建立 20 条以上的第一版评测集；
- 实现纯向量 baseline 报告；
- 定义候选、分数、过滤原因和最终引用的数据协议；
- 设计 Trace 中的检索折叠面板。

### 迭代 7：Query Rewrite 与双路召回

- 补充标题路径、页码、chunk Token 和内容 Hash 等检索元数据；
- 实现按需 Query Rewrite 和失败回退；
- 新增 `tsvector`、GIN 索引和关键词召回；
- 保存 original/rewritten query 与双路原始候选；
- 对比纯向量和双路召回指标。

### 迭代 8：融合、阈值、多样性与 Trace

- 实现 RRF；
- 用评测集校准阈值；
- 实现相邻 chunk 去重、单文档数量限制和可选 MMR；
- 将最终片段接入 Context Builder 的 RAG Token Budget；
- 完成检索 Trace 和对比评测报告。

### 迭代 9：真实停止生成

- generation AbortController 注册表和取消 API；
- 模型、工具、Rewrite、检索和摘要统一取消；
- 前端停止、状态机、竞态与重新生成；
- 越权、重复取消和完成后取消测试。

### 迭代 10：异步文档入库

- BullMQ 任务、Worker、进度状态和失败重试；
- Hash 幂等、取消补偿和 Worker 恢复；
- 前端任务卡片、刷新恢复和自动更新知识库。

### 迭代 11：有指标依据的性能优化

- Query embedding 缓存；
- 绑定用户、知识库和索引版本的检索缓存；
- P50/P95、缓存命中率和模型调用节省报告；
- 根据评测决定是否增加模型 reranker。

## 暂不调整的技术方向

- 不迁移 Next.js：当前聊天产品核心不依赖 SEO、SSR 或 ISR。
- 不优先 OAuth/RBAC：当前用户级知识库隔离足够，团队协作出现前不扩大权限模型。
- 不照搬博客目录和阅读进度：可转化为引用预览和关联文档，但不进入当前主线。
- 不优先多 Agent、MCP 市场和知识图谱：会分散单 Agent RAG 深度。

## 秋招讲解主线

重规划后的项目可以形成清晰叙事：

1. 前端用结构化 SSE、断流重放和 Trace 管理复杂 Agent 状态；
2. 后端用 Tool Registry、权限校验、超时和取消控制 Agent 风险；
3. Context Builder、Token Budget 和 Summary Memory 控制多轮上下文；
4. Query Rewrite、双路召回、RRF、阈值和多样性提升检索质量；
5. 离线评测证明策略收益，Trace 解释每个引用如何产生；
6. BullMQ 和缓存进一步处理吞吐、恢复和成本问题。

这比单纯罗列 LangChain、pgvector、Redis 更容易在面试中自圆其说。
